# ADR 0023: Recovery through an existing linked contact

Status: Accepted for local sandbox identity. Live delivery and assisted recovery are not configured.

AUTH-001 and MARKET-001 / FS-01 require account recovery with verified proof and session revocation. Provide a signed-out recovery flow using an already linked mobile or email. Do not create an account, merge identities, change contacts or infer residence/police verification. Recovering without any linked contact remains unavailable pending a reviewed assisted-recovery policy.

ChallengeService owns the recovery purpose, request rate/expiry/attempt rules, existing-contact lookup and recovery transaction. Request behavior is independent of account existence; only a correct purpose/session-bound proof reaches account lookup. Unknown contacts receive no account or authority. Successful proof needs explicit confirmation to end existing sessions. A prior sign-in or linking proof cannot substitute for a recovery proof.

V28 adds auth_generation and auth_recovered_at to the account. Recovery locks the account's generation advisory key and existing registry rows in deterministic order. It consumes the recovery proof, revokes registry sessions, deletes framework sessions, advances generation/profile version and recovery cutoff, and writes audit plus one security notice transactionally. Earlier sign-in/recovery challenges are rejected by the cutoff rather than rewriting all challenge rows. Profile-bound proofs become stale, and revoked registry tombstones deny old cookies even if an in-flight framework save restores session data.

Ordinary sign-in now returns an internal VerifiedAccount with generation, while its public Account contract stays unchanged. Both verification and session registration synchronize with recovery. Registration rejects a generation superseded after proof verification. This closes the gap between the proof transaction and cookie/session registration; neither client input nor a stale proof establishes authority after recovery. A new code issued after recovery can still sign in: this is not contact replacement or a guarantee against a compromised contact.

Session establishment and browser cookie delivery remain a separate boundary after the recovery transaction. A registration failure or lost response can leave old sessions revoked without a usable new cookie. UI recovery offers current-session check or ordinary sign-in with a new code, never blind replay of the consumed proof. Database/audit failure before commit rolls recovery effects back. HTTP cookie delivery is not claimed to be transactional with PostgreSQL.

The public `/account/recovery` UI uses typed contracts, explicit confirmation, memory-only proof fields and POST forms, masked target/expiry, input errors, pending state, safe request retries and uncertain verification guidance. Sandbox codes use the private inbox; no real email/SMS or verified contact ownership is claimed.

FoundationIntegrationTest covers linked email/same workspace, old-session denial, old sign-in/recovery proof rejection, purpose/session isolation, wrong/expired proof, explicit confirmation, unknown-contact non-creation, audit rollback and the deterministic pre-recovery-proof/post-recovery-registration interleaving. account-recovery.spec.ts covers desktop/mobile flow, keyboard confirmation, axe/reflow, same account, security notice and lost-response guidance. Contact replacement/unlinking, all-contact loss, merging, live notifications, abuse/retention and provider policy remain separate incomplete work.
