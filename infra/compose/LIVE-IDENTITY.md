# Live SMS and email sign-in

The default stack stays sandbox-only. The opt-in live sign-in implementation uses **Twilio Programmable Messaging** for SMS and **Resend** for email. These are replaceable adapters, selected as implementation defaults while no existing provider configuration was supplied. No account was purchased, sender approved, API key invented or real message sent during implementation.

## Required configuration

1. Obtain a Twilio account and approved Messaging Service/sender/route for the intended Indian recipients. Confirm the exact message template, sender registration and any applicable India onboarding with the provider. Put the actual approved text in `LMT_APPROVED_SMS_TEMPLATE`, replacing only its code with `{code}`. The application does not certify approval.
2. Verify the sending domain/address with Resend and obtain an API key permitted to send from it. `LMT_EMAIL_FROM` is a bare email address, not a display-name expression.
3. Provide an HTTPS certificate/key for the chosen public origin. Backend sessions use Secure/HttpOnly `__Host-lmt_session` cookies. HTTP and the `local` profile cannot enable live identity.
4. Select `LMT_IDENTITY_HOURLY_LIMIT` explicitly: this is the instance-wide rolling-hour challenge cap, in addition to the existing destination/session limit. Up to three explicitly rejected/retry-safe submission attempts may occur per challenge; this is not a monetary billing limit. Provider-side spend limits and abuse monitoring are still required for rollout.

```sh
python3 scripts/prepare-live-identity.py
# Edit .local/live/runtime.env using infra/compose/live.env.example.
# Supply the files listed below using your secret manager/editor, not chat or Git.
./scripts/compose-live.sh config --quiet
./scripts/compose-live.sh build
./scripts/compose-live.sh up -d --wait
```

Required files under **`.local/live/`**:

| File | Value |
|---|---|
| `runtime.env` | Exact HTTPS origin, chosen request cap, Twilio Account/Service SIDs, verified sender and approved SMS template |
| `twilio_auth_token` | Actual Twilio credential |
| `resend_api_key` | Actual Resend API credential |
| `tls.crt`, `tls.key` | Certificate chain and corresponding private key |
| `bootstrap_password`, `migration_password`, `runtime_password`, `session_key` | Independently generated by preparation script; retain with this database |

The host directory must remain mode 0700. Compose file-backed secret files must be readable by container UIDs (the existing local setup uses file mode 0444 inside that owner-only directory). Keep `runtime.env` owner-only. Never commit files or put provider keys in `NEXT_PUBLIC_*`, frontend bundles or browser storage. Provider credentials are mounted into the worker, not web/edge/API. API and worker share the OTP secret; rotating it invalidates outstanding codes, so drain/expire pending challenges first. Database/password rotation must be coordinated; the preparation script never overwrites existing secrets.

The overlay uses a **separate `lmt-live` project and volumes**, preserving the sandbox database. Only TLS ingress at loopback port **3443** is published; expose it through your approved production ingress as a separate deployment decision. Set the exact browser-facing HTTPS origin accordingly. The worker alone gets an outbound network for provider calls. The backend's provider hosts are fixed; untrusted request data cannot supply callback or network URLs.

## User journey and scope

At the live origin, choose Mobile or Email, enter contact/name, and request a code. UI reads runtime identity configuration: it shows live delivery guidance instead of a private-inbox notice. The Java API commits challenge and delivery intent before the worker calls a provider. A received code is verified server-side, creates or reuses a **live** account, rotates the session, and opens the account page. Existing rate limits, expiry, attempt limits, CSRF and revocation checks apply.

Live and sandbox identities cannot authenticate each other and are never automatically converted or merged. Use the separate live database. Workspace provisioning, contact linking, reauthentication and assisted recovery retain their separate sandbox/unavailable gates; this delivery enables sign-in/registration only. No live payment or complete rental lifecycle is implied.

## Delivery truth and recovery

- `pending` / `dispatching`: durable work awaiting or submitting to the provider.
- `accepted`: provider acknowledged submission. **Not** a handset/inbox delivery receipt.
- `unknown`: submission outcome cannot be established. A received code still verifies until expiry. The system does not fabricate delivery success.
- `failed`: provider rejected the request; review credentials/sender configuration.
- `expired`: code can no longer establish a session.

Email sends carry a stable `Idempotency-Key` per challenge. Safe retries reuse identical code/content within the five-minute lifetime. SMS HTTP timeouts, lost acknowledgements and ambiguous server outcomes are not automatically resent. A crash after dispatch with no saved reference becomes unknown; inspect provider logs for reconciliation. No resend is issued merely because the browser refreshes or retries the same idempotent request. Explicitly requesting a new code creates a separate request/message under the configured limits.

Provider references and sanitized outcomes are retained in `auth_delivery`; audit records contain IDs/status only, not OTPs, contacts, raw bodies or credentials. Provider callbacks are **not configured** in this slice; no unsigned callback is accepted. `accepted` remains submitted status, and possession of the correct code establishes sign-in. Carrier delivery webhooks, provider reconciliation dashboards, retention, comprehensive abuse controls and production capacity/incident gates remain separate work.

## Verification evidence and remaining live gate

`LiveIdentityIntegrationTest` runs real HTTPS API calls with PostgreSQL, Secure/HttpOnly sessions, and the actual SMS/email adapters aimed at **isolated test HTTP servers**. `LiveOtpTransportTest` verifies rejection/unknown outcomes and stable email idempotency. These are contract fixtures, **not proof of real provider delivery**. Existing Compose browser smoke/contact flows exercise the updated UI and sandbox regression.

Before calling live delivery verified, provide the real sender credentials and TLS configuration, then complete a controlled sign-in with both an authorized phone and mailbox, inspect provider records and verify returning-account/session behavior. That live acceptance check was unavailable during implementation because provider credentials, sender approvals and certificates were not supplied. Do not substitute sandbox inbox codes for this gate.
